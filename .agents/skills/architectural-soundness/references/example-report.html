Journal: system architecture

Draft 4: checked against the template code, diagrams redrawn (Oct 8)
1

Overview

Journal is a texting-style diary that lives entirely on one iPhone. It is built on our Expo template: we keep the template's plumbing (database, settings storage, navigation) and replace its habit demo. No accounts and no server, because privacy and simplicity matter more than sync. This section covers what's in version one, what's not, and why.

Purpose

Journal is a private journal that feels like texting yourself. Notes, photos, clips and check-ins are messages in a chat, grouped by day. One pinch moves between three views of the same entries: Daily (the chat), Weekly and Monthly. The intended user is someone like Henry, who texts himself, wants to look back on his days, and wants reminders about things later.

Scope

In version one

  • Daily chat, Weekly, Monthly, pinch between them
  • Notes, photos and clips, check-ins
  • Replies in threads, one reaction per entry
  • Reminders with real notifications
  • Real location, Apple Maps, nearby places, photo places
  • Haptics, sounds, light and dark mode

Not in version one

  • Accounts, a server, sharing, friends
  • iCloud sync (CloudKit), export, or backup of our own
  • Editing or deleting entries
  • Paywall (code kept, switched off)
  • Share sheet, widgets, Siri, iPad, Android
  • App lock (Face ID)

Context

What the person experiences
  • No sign-up. Open the app and start writing.
  • Nothing is ever asked until they tap something that needs it.
  • Their journal is never sent to anyone. The only copy outside the phone is their own iPhone backup, if they have it turned on.
Technical translation
  • iOS only (iPhone). Expo SDK 55, React Native 0.83, New Architecture.
  • Built on expo-local-first-paywall-template. Its plumbing stays: database, preferences, router, styling, onboarding and paywall code. Its habit demo (habits table, app/(tabs), app/habits, app/create.tsx) is replaced.
  • App identity changes in app.config.ts: name Expo Starter → Journal, bundle id com.expostarter.base → our own, scheme ltstarter → journal, supportsTablet: true → false.
  • The ios/ folder is generated by expo run:ios / prebuild and is not committed. All native settings (permission texts, plugins) live in app.config.ts.
  • No backend. No running costs except the Apple Developer account.
  • One developer. The MVP aims to be fast to build, cheap to run and easy to maintain.

Architectural goals

Four goals, ranked, decide every trade-off: feel, then privacy, then simplicity, then respectful permissions. When two clash, the higher one wins. For example, we accept slower building to get gestures that feel physical. Each card says what the goal costs us.

Ranked. When two goals conflict, the higher one wins.

1 · Feel

It feels native and physical

Pile throws, pinch zoom and the hold menu match the prototype and run smoothly.

Tech: Reanimated and Gesture Handler on the UI thread, custom components where libraries fall short, native iOS modules where they help (hold menu, nearby places).

Gives up: build speed.

2 · Privacy

No journal data leaves the phone

No account and no server of ours. Private like Messages. Apple map and place lookups send only a location, never journal content.

Tech: All data stays in the app's Documents folder. No iCloud sync or CloudKit, no analytics SDK. Only Apple's opt-in crash reports. iOS's own device backup includes the folder by default.

Gives up: sync, export and detailed crash data.

3 · Simplicity

One app, few moving parts

Easy for one person to build and keep working.

Tech: One database, one media folder, no backend, the template's stack, fallbacks listed for each risky library.

Gives up: flexibility for later features.

4 · Respectful permissions

Ask only at the moment of action

Location, notifications and photo places are asked for only when needed, with a way back from "no".

Tech: One permission helper handles every request and links to Settings.

Gives up: nothing meaningful.

Not a goal now: growing to many devices or users. A single phone holds years of entries comfortably.

Your answers that shaped this section

When we must trade, what wins?Feel firstCustom gesture and animation work comes before using ready-made libraries.
How private on the phone?Like MessagesNo app lock. Notification text shows the entry. iOS "Show Previews" covers the lock screen.

Component diagrams

Inside the app there are three layers. Screens take taps. Services do the work. Storage keeps the result. Every save goes through the Journal store, which checks the rules and writes to the database. Screens never save anything themselves. When the database changes, the screens redraw on their own, so there's a single source of truth and nothing gets out of step. The map shows who calls whom. The table and build notes say what each piece is built with. The last two parts cover Check in and photo places in detail.

High-level architecture

All screens sit on one expo-router Stack. The template's tab bar is removed.

Every screen redraws from the database when it changes (drawn once, to Daily chat). Feel has no arrows: it only plays light taps and sounds.

Build notes per module (technical detail)
  • Daily chat: FlashList 2 has no inverted prop. Newest-at-bottom uses maintainVisibleContentPosition: { startRenderingFromBottom: true, autoscrollToBottomThreshold }. Input bar on react-native-keyboard-controller.
  • Overlays: hold menu is react-native-ios-context-menu. Nearby is an expo-router formSheet with sheetLargestUndimmedDetentIndex set, because the story needs no dimming behind it (the default dims). Thread is a frosted overlay. Try a sheet first, fall back to an in-screen overlay.
  • Permission helper: re-checks on AppState foreground so changes made in iOS Settings are picked up. Opens Settings with Linking.openSettings(), as the template's NotificationItem already does. Photo places is an in-app consent, not an iOS permission (see below).
  • Reminder scheduler: saves the time, schedules or cancels the iOS notification, saves its id. On launch, future reminders only: cancel orphan alarms, reschedule missing ones.
  • Place finder: made with create-expo-module --local in modules/place-finder, autolinked. MKLocalPointsOfInterestRequest for places and MKMapSnapshotter for card images, saved as files.
  • Media importer: the picker returns files in a temporary cache. Copy into Documents/media/, then insert the row in a transaction, and delete the copy if the insert fails. A full disk shows an error. Reads when and where the photo was taken from its EXIF.
  • Storage: useLiveQuery needs enableChangeListener: true (already set in db/drizzle.ts). Migrations via useMigrations, generated by bun run db:generate. Preferences in MMKV via lib/storage.ts. zustand is only used by the template's portal primitive. Migration gate: today useMigrationHelper() runs only in app/(tabs)/index.tsx. Move it to app/_layout.tsx before deleting the tabs, so nothing reads the database before its tables exist.
  • Paywall gate: wraps components/OnboardingGate.tsx and the configureRevenueCat() call. A constant, not a stored preference, so no saved value can turn it on.

Photo places: privacy approach

What the person experiences
  • Picking a photo never asks for anything.
  • The first time they open a map of their photos, Journal asks once: "Show your photos where they were taken? Journal uses the location saved in each photo. It stays on this phone."
  • "Not now" keeps photos working, just with no map pins. They can turn it on later in Journal's Settings.
Technical translation
  • iOS has no "photo places" permission. The picked file can carry its location in EXIF, unless the photo has none or the person removed it in the picker. Read it with expo-image-picker exif: true and confirm on a device in the photo spike.
  • Don't request full Photos library access (expo-media-library) just to read locations. It's a bigger ask than the feature needs.
  • Coordinates are saved with the media row, on the phone. The copied file already contains them, so this adds no new exposure.
  • The one-time question is an in-app consent stored in MMKV (photoPlaces: on | off). ensure("photoPlaces") shows it instead of an iOS prompt.

Data models

Everything the person adds is one kind of record, an entry, saved in one on-phone database. A photo or a check-in adds an optional extra record. A reply is just an entry that points to its parent. Photos are copied into the app's own folder, so they survive being deleted from Photos. The two flow diagrams show the order of steps that keeps the database and the files (or the iOS alarm) in step when something fails.

What the person experiences
  • Everything they add shows up on the day they added it, like a text.
  • A photo stays in the journal even if it's deleted from Photos.
  • Each entry can have one reaction, one reminder and many replies.
  • Nothing can be edited or deleted in version one.
  • If the phone is lost, the journal is lost, unless they restore a new phone from an iPhone backup.
Technical translation
  • created_at and local_day are set in JavaScript from the device clock and time zone. Not the template's SQL CURRENT_TIMESTAMP, which is UTC and puts late-evening entries on the wrong day.
  • Media paths are relative to Documents (media/abc.jpg). The app's folder path changes between installs and restores.
  • Reaction and reminder are fields on the entry. A reply is an entry with a parent_id.
  • Add-only. Only reaction and reminder fields ever change.

Database schema

Draft Drizzle tables in db/schema.ts, replacing the template's habits table. Names may change; the structure is the decision.

Preferences (outside the database, in MMKV through lib/storage.ts): appearance (template key theme), sounds on or off, last view. Whether a permission was granted is always read live from iOS, never cached. The paywall switch is a code constant, not a preference.

Data flow

Adding a photo: copy first, then record, then show. A failed record removes the copy, so no stray files.

Setting a reminder: the database is saved first and the iOS alarm follows it. If a step fails, the launch check repairs it.

Interface definitions

There's no web API. The "interfaces" are the handful of calls the app's modules make to each other, plus one link from a tapped reminder into the app. The first table lists those calls, which are the arrows on the section 4 map. The second lists the rules every piece of data must follow, all checked by the Journal store before saving.

What the person experiences
  • Everything happens inside the app.
  • The only way in from outside is tapping a reminder.
  • Nothing waits on a server of ours. Only maps and Nearby need internet, for Apple's services.
Technical translation
  • There is no web API. The "APIs" are the boundaries between modules inside the app.
  • One deep link: journal://entry/{id}, carried in the notification's data.url. This needs the scheme changed from ltstarter and an expo-router route app/entry/[id].tsx. Taps are handled with Notifications.useLastNotificationResponse(), which covers cold starts too.
  • One custom native bridge: the Swift place-finder module. Everything else uses Expo or community modules.

Risk and mitigation

The biggest risk is time, not technology: custom gestures may take longer than planned. That's why they get built first, on a real device. Other risks are smaller or accepted. For example, losing the phone without a backup loses the journal. The map places each risk by how likely and how bad it is. The table gives the response to each.

Risk map

Placed by how likely and how bad each risk is. Act on the top-right first.

Mitigation strategies

RiskMitigation
Custom gestures run longBuild pile, pinch and hold menu first, as spikes on a real device. Cut scope elsewhere before simplifying motion.
Library falls shortUse the fallbacks in the user stories: own hold menu, gesture-image-viewer, own month rows, expo-maps.
Phone lost or resetAccepted. iOS device backup includes Documents/. Confirm once with a real backup and restore before release, and say so plainly in Settings.
Update breaks saved dataBefore release, replace the two habit migrations with one baseline. After release, additive migrations only, each tested on a copy of a real journal.
Photos fill the phoneKeep clips short. Revisit smaller copies if people complain.
Reminders out of stepDatabase first, alarm second. Launch check repairs future reminders.
Crashes go unnoticedCheck Xcode Organizer after each release. TestFlight on a real device.
Paywall shows by accidentFirst build task: gate it with PAYWALL_ENABLED = false. Before each release, a fresh install must open straight to Daily.
No internet, or Nearby finds few placesClear messages per situation (see Check in in section 4). Check-in cards keep their saved map image.

Development workflow

The app runs as an Expo development build (expo-dev-client), not Expo Go, because it has native code Expo Go doesn't include. Most days, only Metro is needed.

ChangeWhat to runSpeed
JS/TS only: screens, styles, logic, Drizzle schemaLeave bun run dev running. Saving reloads the app. After a schema change, run bun run db:generate first.Seconds
Native: adding a package with native code, editing app.config.ts plugins or permission texts, changing the Swift module, changing app name, bundle id or schemebunx expo prebuild --clean, then bun run ios. Plain expo run:ios skips config changes once ios/ exists. --clean is safe because ios/ is generated. If CocoaPods fails with a Unicode error, set LANG=en_US.UTF-8.Minutes

Most version-one native packages are not installed yet. Batch their bunx expo install calls to rebuild fewer times.
