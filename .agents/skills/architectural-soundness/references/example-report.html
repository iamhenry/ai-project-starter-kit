Pull Requests in BB · Draft 4

The proposed system

One place to see which pull requests need you.

A read-only page inside BB groups pull requests by what needs attention, explains their status, and sends you to GitHub when you are ready to act.

Recommended architecture

GitHub keeps the facts. BB organizes them. The existing signed-in GitHub helper connects the two.

The 80 percent answer: build the complete read-only loop first. Do not recreate GitHub actions or storage inside BB.

1Requirements

What this needs to do

Start with the experience you need, the promises it should keep, and the real-world limits it has to work within.

DO

What you need to accomplish Features

  • Show pull requests across repositories
  • Group what needs review, what is mine, and what changed
  • Explain review, checks, draft, and merge status
  • Search, refresh, preview, and open in GitHub
BE

What you should be able to trust Quality

  • Feel current without repeatedly hitting GitHub
  • Label stale, partial, or unavailable information honestly
  • Keep working when one group fails
  • Keep credentials out of the browser and logs
FIT

What already shapes the solution Constraints

  • One local user for the first version
  • Existing BB plugin navigation and server patterns
  • An installed and signed-in GitHub CLI
  • GitHub remains the source of truth

What you can trust now Reliability

  • One failed group does not hide successful groups.
  • Old results are labelled with their age.
  • Unexpected GitHub output is rejected.
  • Users can retry; no user data is lost.
  • Safe logs describe events without credentials.
5Trade-off analysis

Why we are choosing this approach

Every option can put pull requests on a page. Only one currently gives you the complete view without first building a new GitHub login and connection system.

Is the system complete

Ready for implementation planning.

The read-only design covers the user journey, gives every necessary behavior a home, protects credentials, fails honestly, and has explicit conditions for future change.

Every important job has an owner Soundness

  • Attention and navigation belong to the BB page.
  • Queries and status rules belong to the plugin engine.
  • Authentication belongs to the existing GitHub helper.
  • Pull request truth belongs to GitHub.
  • Freshness and recovery are visible to the user.
Decision record

How we arrived here

  1. September 10 · Starting point

    Bring pull request attention into BB

    The initial idea was a GitHub Dash-style view that makes many pull requests easier to track from one simple place.

  2. September 10 · Scope

    Keep the first version read-only

    Tracking is the proven need. Comments, approvals, merges, checkout, and notifications stay in GitHub until real use justifies their cost and risk.

  3. September 10 · Existing system

    Use a global BB page and protected plugin logic

    Existing BB plugins prove the navigation and page-to-server pattern. BB’s environment data cannot supply a complete cross-repository list.

  4. September 10 · Connection

    Reuse the signed-in GitHub helper

    The GitHub CLI is already present and authenticated. Reusing it avoids a new token system while still covering accessible repositories.

  5. September 10 · Report

    Teach the architecture visually and in plain English

    The report now moves from the whole system to its pieces, subsystem behavior, growth limits, and trade-offs, with technical terms kept as supporting labels.

Assumptions and handoff

What we established

  • BB supports global plugin pages.
  • The GitHub CLI is installed and signed in.
  • BB’s known PR data is not a complete cross-repository source.

What version one assumes

  • One local user.
  • Dozens rather than thousands of visible results.
  • Manual refresh is enough.
  • GitHub remains available for all write actions.

What implementation planning decides

  • Which GitHub facts each row needs Data model
  • The plain-English status rules
  • How briefly to keep the last answer Cache
  • The exact page-to-plugin request API contract
